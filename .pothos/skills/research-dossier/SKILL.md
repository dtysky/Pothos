# Research Dossier

## 目的

用于把一次明确问题、旅程、地点、作品或主题的调研，整理成可保存、可引用、可用于后续创作判断的报告。

本技能服务 `research/`，不是 `.pothos/knowledge/` 的长期记忆维护，也不是 `projects/*/research/` 的大型项目研究。

## 何时使用

当用户提出以下需求时使用：

- 为某次旅行、拍摄或观影做文学、历史、地理、社会背景调研
- 把外部资料整理成一份完整报告
- 研究一个暂时不属于大型项目的专题
- 将一次聊天中的资料性成果落地为可回看的案头文件

## 落点

默认写入：

```text
research/
```

文件命名优先使用：

```text
YYYYMMDD-topic-scope.md
```

当明确接收 Pharos 某个 `trip_id` 的创作资料委托时，只维护研究内容：

```text
research/YYYYMMDD-topic-scope.md
```

Markdown dossier 是人类阅读与研究内容真相源。面向 Pyxis 的 `field-guide.json` 由 Pharos
从确认版 dossier 编译、维护和发布；Pothos 不创建、修改或校验它，也不维护 `plan.json`、
`record.json` 或 `trips.json`。

如果调研后续升级为大型项目，再迁移到：

```text
projects/<project-code>/research/
```

## 工作流

### Step 1

先确认调研是否属于大型项目。

- 如果属于现有大型项目，写入该项目的 `research/`
- 如果不属于大型项目，写入顶层 `research/`
- 如果只是长期稳定的用户画像、文风规律或项目方法论，改用 `knowledge-curation`

### Step 2（Pharos 交互研究会话）

当任务由 Pharos 的 `research-request.md` 派发，且提示中包含旅程名、`trip_id` 与交回约定时，
先进入交互研究状态，不要立即生成完整 dossier：

1. 读取研究委托、当前行程 / 作品映射和已有资料包；把已有内容当作可质疑的草案。
2. 每轮只提交一小批来源、地方线索或问题候选，让用户能够逐项判断。
3. 候选应说明“它是什么、为什么可能有用、来源或不确定性、建议关联的作品 / 地点 / 分类”。
4. 接受用户对候选做保留、排除、暂存、跨作品或跨地点关联、重新归类和继续追查；不要强迫
   新资料立刻进入唯一的文学 / 历史 / 政治等格子。
5. 保持一份会话内决策账：已采纳、暂存、排除、待补查，以及用户对问题意识和分类的修正。

只有用户明确说“交回 Pharos”，才结束交互研究并执行后续落地步骤。普通的“先看看”、
“继续查”或对单条材料的认可，都不构成交回指令。

### Step 3

先按旅程长度和实际停留时间选择值得深入的问题，再明确报告结构。停留时间决定选题数量，
不决定已选问题的知识完整度；不能因为行程短，就把重点地点的地质、水文、历史或生活背景
压缩成几句概述。不要把已有 dossier 的主题权重直接套给新路线；尤其不得因为前一次研究
重视产业、治理或制度，就在自然旅行中继续维持相同重心。

行前资料包通常采用“综述—分地点—结论”的人类阅读结构。调研时可用以下四个问题检查
材料是否完整，但它们只是后台检查表，不是每个地点必须重复的四个标题：

1. 自然基础：这个地方为何形成今天的地貌、水系、生态或物产？
2. 历史与生活：人怎样使用、组织并改变这里？
3. 当代处境：今天正在发生什么变化，哪些变化会影响理解或旅行？
4. 饮食与物产：当地人怎样处理和食用本地材料？

成文时只保留与地点真正相关的主线，并按解释力排序。重点不等于简写：一条主线一旦入选，
正文要回答其基本因果链，而不是只给结论或观看提示。

- 自然景观是主线时，按需说明地质年代与区域构造背景、主要岩性或沉积过程、抬升 / 断裂 /
  侵蚀等演化阶段、现代地貌形成机制；涉及河流时，至少核实源头、汇流关系、流向与流域、
  季节性水文和河流如何塑造聚落或景观。应区分“山系如何形成”“景区地貌如何形成”和
  “今天看到的表面过程”，不得用一个笼统的地貌名称代替演化史。
- 人文是主线时，建立必要的时间层次，说明聚落、交通、生产、贸易、信仰、教育或制度如何
  进入地方；不能只罗列遗址和名人，也不能把复杂历史缩成一个文化标签。
- 行政、治理和保护现状只在直接影响地方理解、社区生活或旅行边界时出现，不得为了栏目
  完整而填充。

通常至少包含：

- 调研对象与问题意识
- 核心结论
- 分主题或分地点研究
- 文学、历史、社会或影像顾问式解读
- 可用于创作或现场观察的问题
- 资料来源

Pharos 创作资料包保留两种阅读尺度，但不得机械重复同一套栏目：

- 作品章节：以 Pharos 已确认的作品主题为一级结构，包含综述、分地点研究与结论；每章只
  深入一两个足以支撑观看的问题，其余材料简要交代；
- 地点内容：说明地点在本章中的作用，再按自然、历史与生活、当代变化、饮食等实际相关
  方向组织。摘要、现场问题和容易误读之处按需出现，不要求每个地点等量填满。

食物不另建探店页，默认不推荐具体商家。对资料足以核实的地方代表食物，尽量完整收录，
不要为了篇幅预先限定品类数量。可按主食、小吃、菜肴、汤羹、甜食、饮品或物产分组，用
一至数句说明名称、主要原料、基本做法和常见食用场景，使陌生旅行者获得可用的饮食地图。
只有名称而无法核实做法或地方关系的项目不硬写，可列为待查。

在完整概览之上，再挑选少数同时具有代表性、名称或做法辨识度、地方解释力和可靠来源的
食物重点展开。重点食物应有独立小标题和两三段正文，至少说明原料 / 做法、食用场景或地方
关系、今天的变化，以及史料与传说的边界；不能只多解释一句便称为重点。概览的完整性与
重点的深度并不冲突。

资料包首先是一份知识调研报告，其次才服务旅行中的理解和选择。地点正文以事实、演变与
解释为主，不穿插“应该看什么”“怎样拍”“资料要帮助什么”等行动指令或写作元话语。
路线取舍、现场观察和影像关联如确有价值，集中放在章节结论或独立的“与本次行程的关系”
小节，篇幅明显短于研究正文。

不把研究问题改写成必须完成的采访、观察或拍摄任务。作品与地点只建立问题框架和素材池，
不预写口播或成片结构。文字使用朴实的调研文体，避免清单式命令、连续的“不要 / 不必”、
抒情游记、VLOG 口吻，以及解释作者为何这样写的过程性语言。

篇幅以所选问题是否讲清为准。作品简介通常不超过约 300 字；普通地点可用约 800–1500 字，
承担自然或历史主线的重点地点可以达到约 1500–3000 字，必要时更长。旅程较短时减少并列
专题和地点数量，而不是截断重点问题的因果链。不得靠重复措辞或资料堆砌凑数。

### Step 4

写作时区分：

- 事实：来自资料、文件或可靠来源
- 推断：基于事实作出的解释
- 建议：面向创作、拍摄、阅读或行动的判断

dossier 可通过措辞、引文和必要的段内提示区分事实、推断与建议，不要求每段都加同样的
分类标签。保留稳定的作品 ID、地点 ID 和来源 ID，供 Pharos 映射到传输协议。事实章节
必须引用来源；涉及当代政策或治理的事实来源必须保存核验日期。文学与影像作品只介绍作者、
背景、内容和阅读价值，不得复制大段受版权保护的原文。

营业、交通、天气、空域等短期执行信息继续交给 Pharos 临行核验，不写入长期资料包。

### Step 5

落地前检查：

- 是否误写到了外部项目
- 是否误塞进 `.pothos/knowledge/`
- 是否缺少来源
- 是否只是资料堆砌，而没有形成可用判断
- 是否把研究正文写成了“应该看什么 / 拍什么”的行动建议
- 重点自然地点是否交代了形成时间、演化过程和水系来源，而不只是地貌名称
- 饮食概览是否因人为限定数量而漏掉已有可靠资料的代表食物

### Step 6（交回 Pharos）

当用户明确说“交回 Pharos”时：

1. 读取委托指定的当前 `plan.json`，确认 dossier 使用的作品 ID、地点 ID 和路线名称仍与
   当前旅程一致；发现变化时在交回摘要中说明，不修改 `plan.json`。
2. 将已确认内容整理进 Markdown dossier，并递增 dossier 自身 revision；未确认候选不得
   混入正文。
3. 最终回复提供可机读的交回摘要：旅程 / trip ID、dossier revision、Markdown 绝对路径、
   已采纳的主要变化、仍暂存 / 排除的材料、尚存缺口。
4. 不生成或修改 `field-guide.json`，不调用 Pharos 的 JSON 校验 / WebDAV 工具，也不得
   把“Pothos 已完成”描述为已经同步到 Pyxis。
